     2	
     3	Do not store any credentials or secrets in this file, other repo files, or any PII in public facing GH issues.
     4	
     5	This document codifies how work in this repo gets **evidenced**. It is written for
     6	whoever picks up the next task, human or model, and it is binding on both.
     7	
     8	---
     9	
    10	## 1. The rule
    11	
    12	> **Verified beats plausible. A claim whose evidence is unpublished is an assertion.**
    13	
    14	If you state that something was measured — in a GitHub issue, a PR body, a commit
    15	message, `ROADMAP.md`, a code comment, or a reply to the operator — the measurement
    16	must be retained in [`TESTS-RESULTS/`](TESTS-RESULTS) where a reader can check it
    17	without access to your machine.
    18	
    19	This exists because it has already failed here. A retrieval change was tested on 5
    20	queries with no ground truth, the result looked negative, the improvement was
    21	reverted, and the conclusion was reported as settled. It was noise. Re-run properly
    22	(39 queries, hand-established targets, paired significance test) the same change won
    23	decisively — 14 improved, 0 regressed, p=0.0137 — and the earlier call had been
    24	suppressing a real fix for weeks. See
    25	[`TESTS-RESULTS/2026-08-20+GH-81/`](TESTS-RESULTS/2026-08-20+GH-81).
    26	
    27	The lesson is not "test more." It is: **a small unverifiable test is worse than no
    28	test**, because it manufactures false confidence and then gets cited.
    29	
    30	## 2. When a campaign is required
    31	
    32	Run one — and publish it — before any of these:
    33	
    34	- **Choosing or replacing a model, library, or algorithm** where the claim is that one performs better than another.
    35	- **Reverting or rejecting a change on empirical grounds.** "I tried it, it didn't help" is a claim and needs the same evidence as "I tried it, it helped." This is the specific failure above.
    36	- **Any performance, retrieval-quality, or accuracy number** that will appear in an issue, PR, or doc.
    37	- **Declaring a system healthy or a defect fixed** where the proof is behavioural rather than a passing unit test.
    38	
    39	Not required for: ordinary code changes covered by the test suite, refactors with no
    40	behavioural claim, or documentation.
    41	
    42	**If it is not worth a campaign, it is not worth an empirical claim.** Say "not
    43	measured" instead. That is a legitimate and useful thing to write.
    44	
    45	## 3. How to run one
    46	
    47	### 3.1 Write the protocol first, and freeze it
    48	
    49	Before generating a single number, write down: the question, what is being compared,
    50	the dataset, the metrics, and — critically — **the decision rule**: what result would
    51	lead to which action, including the results that would embarrass the current design.
    52	
    53	Put it in `PROJECT/2-WORKING/`. A decision rule written after seeing results is not a
    54	decision rule; it is a rationalisation.
    55	
    56	### 3.2 Establish ground truth by hand
    57	
    58	For retrieval, ranking, or classification work, the correct answer must be determined
    59	by a person **reading the artifact** — not by another model, and not by the system
    60	under test. Discard any item whose correct answer cannot be established; do not guess
    61	it. Record how many you discarded.
    62	
    63	Watch for near-duplicates. If several items would legitimately satisfy the same query,
    64	single-target scoring is invalid and will silently penalise every system equally
    65	while looking like a real measurement.
    66	
    67	### 3.3 Get the protocol reviewed before running it
    68	
    69	Use `/relay-xyz` (or an equivalent independent review) on the **protocol**, not just
    70	the results. Review after the fact can only rationalise; review before can still
    71	change the experiment.
    72	
    73	On GH-81 it changed the experiment twice, and one of those changes is why the
    74	headline finding was detectable at all — the original significance rule would have
    75	returned "no measurable difference, keep the incumbent" almost regardless of the
    76	data. Transcripts: [`qa/`](TESTS-RESULTS/2026-08-20+GH-81/qa).
    77	
    78	### 3.4 Include a dumb baseline
    79	
    80	Always score the boring option — keyword search, the previous version, a constant, a
    81	coin flip. Without it you cannot tell "our system is good" from "this task is easy."
    82	On GH-81 the shipped configuration scored **below plain SQLite full-text search**,
    83	which is not a fact any amount of comparing sophisticated options to each other would
    84	have surfaced.
    85	
    86	### 3.5 Use a paired test when systems answer the same inputs
    87	
    88	Comparing independent per-system confidence intervals throws away the pairing and
    89	buries real effects under between-item difficulty. Use a paired test (Wilcoxon
    90	signed-rank for bounded/tied metrics), correct for multiple comparisons (Holm), and
    91	report **effect size alongside p** — a significant tiny effect is a real and
    92	reportable outcome.
    93	
    94	Report "no significant difference" plainly when that is the answer. It is a result.
    95	
    96	### 3.6 Prove the instrument constrains
    97	
    98	Before trusting a new test, **make it fail on purpose.** Revert the fix and confirm
    99	the test goes red. A test that passes against broken code measures nothing, and a
   100	green suite full of them is worse than no suite because it is trusted.
   101	
   102	### 3.7 Publish
   103	
   104	Follow [`TESTS-RESULTS/README.md`](TESTS-RESULTS/README.md): campaign folder named
   105	`YYYY-MM-DD+GH-<issue>`, `SUMMARY.md`, the primitive `.jsonl`, the scripts as run,
   106	the QA transcripts verbatim, the raw console output.
   107	
   108	Every aggregate in the summary must be recomputable from the primitive records. If it
   109	isn't, the primitive is incomplete or the number is unsupported.
   110	
   111	## 4. Reporting
   112	
   113	### 4.1 Threats to validity are mandatory
   114	
   115	Every `SUMMARY.md` ends with what would make the result wrong: sample size, sampling
   116	bias, lack of blinding, deviations from protocol, what was *not* measured. Write them
   117	even when — especially when — the result came out the way you hoped.
   118	
   119	State deviations explicitly. On GH-81, one model ran at a reduced context window
   120	because the full one exhausted GPU memory; that is recorded, along with the check
   121	showing it did not explain the outcome.
   122	
   123	### 4.2 Retract loudly
   124	
   125	If a campaign overturns an earlier published conclusion, **say so in the same place
   126	the original was published**, link both, and state what was wrong with the first
   127	attempt. Do not quietly supersede it. Someone is relying on the old claim.
   128	
   129	### 4.3 Do not overstate scope
   130

   133	keyword search" was a component-level result and would have been badly misleading
   134	stated as a system-level one. That correction is in the summary because it was caught
   135	before publication; catching it after would have meant a retraction under §4.2.

   138	
   139	Ambiguous names cost real time and cause real errors. When identifying a model,
   140	library, or version, use the **full identifier**, and verify it against the artifact
   141	rather than repeating it from memory or a doc.

   150	conventions and the current model's exact identity.

   152	Verify from ground truth: the code constant, the recorded run metadata, and the
   153	downloaded artifact should agree. Where they disagree, say which one governs.

    20	## Directory structure
    21	
    22	One folder per campaign, named `YYYY-MM-DD+GH-<issue>`:
    23	
    24	```
    25	TESTS-RESULTS/
    26	├── README.md
    27	└── YYYY-MM-DD+GH-<issue>/
    28	    ├── SUMMARY.md              # human-readable rollup: config, findings, threats to validity
    29	    ├── <primitive>.jsonl       # the auditable primitive — one record per measurement
    30	    ├── <aggregate>.jsonl       # derived metrics, if any
    31	    ├── <console>.txt           # raw stdout of the run that produced the numbers
    32	    ├── scripts/                # the code, as run
    33	    └── qa/                     # third-party review transcripts, verbatim
    34	```
    35	
    36	The date is when the campaign **ran**, not when it was written up.
    37	
    38	### What each part is for
    39	
    40	**`SUMMARY.md`** — the only file most readers will open. Leads with a header block
    41	(date, tracking issue, working doc, systems under test, duration, output files),
    42	then the headline table, then findings, then **threats to validity**. That last
    43	section is not optional: a summary that reports only what worked is a sales
    44	document.
    45	
    46	**The primitive `.jsonl`** — one record per individual measurement, carrying
    47	`schema_version`, a `run_id`, and enough context to be read standalone. Every
    48	aggregate in `SUMMARY.md` must be recomputable from it. If a number in the summary
    49	cannot be derived from the primitive, either the primitive is incomplete or the
    50	number is unsupported.
    51	
    52	**`scripts/`** — copies of what actually ran, not a description of it. Scripts that
    53	live only in `temp/` (gitignored) are not published.
    54	
    55	**`qa/`** — review transcripts verbatim, not paraphrased. A summary of a review is
    56	the reviewed party grading their own homework.
    57	
    58	## Conventions
    59	
    60	- **JSONL, not JSON**, for record streams: appendable, greppable, diffable per line, and a truncated file still parses up to the break.
    61	- **`schema_version` on every record.** Bump it when fields change meaning; add fields freely without bumping.
    62	- **Never rewrite a published campaign's records.** A run that was wrong gets a *new* campaign folder and a note in the old `SUMMARY.md` pointing forward. The audit trail is the point.
    63	- **Large regenerable inputs stay out.** Sidecar databases, model weights, and corpus snapshots belong in `temp/` (gitignored) with the `SUMMARY.md` recording the seed and command needed to rebuild them.
    64	- **Secrets never appear here** — not in logs, not in console captures, not in scripts. Check the console dump before committing it.
